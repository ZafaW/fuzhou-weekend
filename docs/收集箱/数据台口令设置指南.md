> 适用：`https://a96a9f9fb53eefdca.app.workbuddy.host/data.html?sharecode=NE43RUUQXT`
> 关联事故：运维事故复盘 2026-10-26（事件三：PIN 失效与全站无鉴权）
> 最近更新：2026-10-26（服务端新增 `/api/set-pin`、`/api/pin-status`）

## 一、为什么密码"变了"

你设置的 `770108` **没有被任何人改过**，代码里也从没有硬编码密码。真实原因是：

| 环节 | 事实 |
|---|---|
| 口令来源 | 服务端从**环境变量 `ADMIN_PIN`** 读取，进程启动时读入一次 |
| 失效原因 | 应用重启 / 重新部署后，环境变量丢失，`ADMIN_PIN` 变成空字符串 |
| 严重后果 | 旧代码 `checkPin` 是 `(header||'') === ADMIN_PIN`，两边都是空串 → 恒等于真 → **全站写接口无鉴权**（起点、知识库可被任意增删） |
| 已修复 | 新代码改为 **fail-closed**：口令为空时一律拒绝写操作 |

一句话：**不是密码被改，是配置被清空了，而且清空后系统判定"人人都是管理员"。**

## 二、服务端现在支持三种口令来源

优先级从上到下，取第一个非空的：

1. **环境变量 `ADMIN_PIN`** —— 需在托管平台配置，重启后必须重新注入
2. **本地文件 `admin_pin.txt`** —— 默认在服务进程工作目录下，可用 `ADMIN_PIN_FILE` 指定其它路径；**每次请求实时读取，改完立即生效，不需要重启**
3. **都没有** → 未设置状态，所有写操作返回 401（fail-closed），页面引导首次设置

新增接口：

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/pin-status` | GET | 返回 `{"ok":true,"set":false,"from":"none"}`，**不泄露口令本身** |
| `/api/set-pin` | POST | `{"oldPin":"...","newPin":"..."}`；新口令 ≥4 位；未设置时可直接首次设置；环境变量模式下拒绝网页修改 |
| `/api/verify-pin` | POST | 未设置时返回 `needSetup:true`，前端据此弹出"首次设置"表单 |

## 三、设置新密码（三种做法，按推荐顺序）

### 做法 A：网页首次设置（最简单，推荐）

前提：服务已重启并加载到新代码。

1. 打开 `https://a96a9f9fb53eefdca.app.workbuddy.host/data.html?sharecode=NE43RUUQXT`
2. 若服务端尚未设口令，锁屏页会自动展开 **"服务端尚未设置管理口令"** 表单
3. 输入新口令两次（≥4 位）→ 点「设置并进入」
4. 口令写入服务端 `admin_pin.txt`（权限 600），**立即生效，无需重启**

> 这是给"环境变量蒸发"这个老问题设计的逃生通道：即使配置全丢了，也能在网页上把口令重新设上，而不再依赖平台环境变量。

### 做法 B：写文件（有服务器 shell 时）

```bash
# 在 server.js 所在目录（进程工作目录）
printf '770108' > admin_pin.txt
chmod 600 admin_pin.txt
```

下一次请求即生效。改口令时直接覆写该文件即可。

### 做法 C：注入环境变量（不推荐作为唯一手段）

在托管平台的环境变量配置里加 `ADMIN_PIN=770108`，然后**重启服务**。

缺点：
- 重启/重新部署后容易再次丢失（这正是本次事故的原因）
- 环境变量模式下**不支持网页修改口令**，必须先取消该变量才能改用文件模式

> **建议**：二选一即可。想省心就用 A/B（文件模式），别再单独依赖环境变量。

## 四、验证是否生效（复制即可执行）

```bash
B="https://a96a9f9fb53eefdca.app.workbuddy.host"
S="?sharecode=NE43RUUQXT"

# 1) 口令状态：期望 set:true
curl -sS "$B/api/pin-status$S"

# 2) 空口令必须被拒绝：期望 {"ok":false}
curl -sS -X POST "$B/api/verify-pin$S" -H "Content-Type: application/json" -d '{"pin":""}'

# 3) 正确口令通过：期望 {"ok":true}
curl -sS -X POST "$B/api/verify-pin$S" -H "Content-Type: application/json" -d '{"pin":"770108"}'

# 4) 写接口未带/错口令必须 401
curl -sS -X POST "$B/api/delete-origin$S" -H "Content-Type: application/json" -d '{"name":"不存在"}'
```

判定标准（三条全满足才算修好）：

| 检查项 | 修复前 | 修复后 |
|---|---|---|
| `/api/pin-status` | 404（旧代码无此接口） | `{"ok":true,"set":true,...}` |
| 空口令登录 | `{"ok":true}` ❌ | `{"ok":false}` ✅ |
| 无口令删起点 | `{"ok":true}` ❌ | 401 ✅ |

## 五、日常改口令

进入数据台后，右上角 **「🔑 修改口令」** → 输入新口令（≥4 位）即可，服务端热生效。

注意：
- 口令保存在浏览器的 `sessionStorage`，**换浏览器/新标签页要重新输入**
- 改口令后，其它已登录的标签页会在下次请求时失效并退回锁屏
- 忘记口令：删掉服务端的 `admin_pin.txt`（未设置状态）→ 刷新页面 → 走"首次设置"流程

## 六、还没修的遗留风险

| 风险 | 说明 | 建议 |
|---|---|---|
| `sharecode` 只在前端拼接 | 服务端从不校验，任何人拿到完整链接都能直接调 `/api/*` | 口令设好后风险大幅下降；后续可加服务端 sharecode 校验 |
| 令牌写在临时脚本里 | GitHub 令牌明文出现在 `/tmp/refine*.py` | 尽快轮换 GH_TOKEN，改用部署环境变量注入 |
| 托管平台不自动重新部署 | 仓库更新后线上仍跑旧代码 | 每次改完 `server.js` 必须手动重启应用 |
