## 一、背景

每日 07:00 的定时任务按以下链路运行：高德周边检索（围绕 `origins.json` 各起点 80km）→ 合并去重 → 攻略自动补全与 AI 精修 → 生成自包含 `index.html` → 写回仓库并经 GitHub Pages 发布。2026-10-26 上午该链路连续暴露两个缺陷：网页白屏（P0）与起点配置被静默删除（P1）。

## 二、事件一：更新后网页白屏（P0）

### 现象

页面可访问（HTTP 200、307KB），但整页脚本未执行：推荐清单空白、目录与筛选无内容，即俗称的「白屏」。

### 根因（代码级）

`run_daily.js` 的每日保鲜函数 `freshenNotes()` 用正则 `(\{.*\}),?$` 抓取 `SPOT_NOTES` 条目行，把**行尾逗号当作分隔符丢弃**，再以 `'  name: {...}'`（无逗号）整行覆写：

```js
// 事故代码
lines[r] = '  ' + JSON.stringify(name) + ': ' + JSON.stringify(nv);   // ← 行尾逗号被吞
```

结果相邻两条目在 JS 中变成「字符串 + 字符串」→ 整段内联 `<script>` 抛 `SyntaxError` → 页面白屏。

**影响面**：当天保鲜更新 109 行，即 109 处逗号丢失；`index.html` 与模板 `福州带娃周末出行.html` 同时被写坏——模板损坏意味着**次日、次次日会继续崩**，不是一次性故障。

### 修复

1. `setNoteLine()` 统一收口：覆写前检测原行是否有尾逗号并原样保留（保鲜、LLM 提质两条路径共用）。
2. 重建损坏的 `SPOT_NOTES`（231 条），模板与 `index.html` 全部恢复，语法校验通过。
3. 重新发布并实测：无头浏览器渲染零 JS 报错，清单 61 条、内嵌 POI 150。

### 防复发：新增三道闸

| 闸 | 位置 | 行为 |
|---|---|---|
| 闸 1 改动自检 | `freshenNotes()` 结束 | 条目总数必须与改动前一致、每个条目值必须可编译，否则抛错 |
| 闸 2 发布前体检 | 写回 `index.html` 前 | 所有内联脚本交给 V8 编译（只编译不执行），失败即**中止发布、保留线上旧版** |
| 闸 3 发布后回读 | 写回后 | 回读仓库内容，与本地生成内容**逐字节比对**并再次体检 |

模板写回前同样体检——本次事故的污染源正是模板。闸 2 在修复过程中已真实拦截过一次发布，验证有效。

### 根因（已修正）

> ⚠️ 初判为「后端覆盖式写入」，**经查后端代码后修正**：`server.js` 的 `/api/save-origins` 本就是合并语义（读取现有清单 → 追加不存在的 → 写回），`/api/delete-origin` 是精确删除。四次提交实为「加、删、加、删」四次独立操作，与接口语义吻合。

**真正的根因是：起点增删接口完全没有鉴权。**

| 缺陷 | 位置 | 后果 |
|---|---|---|
| `/api/save-origins`、`/api/delete-origin` 未调用 `checkPin` | `server.js` 191 / 222 行前 | 任何知道服务地址的人都能增删起点，无需密码 |
| `checkPin` 在 `ADMIN_PIN` 为空时恒真（fail-open） | `(header||'')===ADMIN_PIN` | 环境变量丢失后，全站写接口（含知识库）实际无保护 |
| 后端不校验 `sharecode` | `server.js` 全文无 share 校验 | 分享码只是前端拼接，不构成访问控制 |

前端其实早已正确：请求带 `x-admin-pin` 头，删除/保存前也有 `ensurePin()` 二次确认。问题全在服务端未校验。

### 修复

1. 立即补回「福建农林大学金山校区」（119.2329, 26.0872），`origins.json` 恢复 2 个起点（commit `be35d7e5`）。
2. 新增**起点守卫**：`run_daily.js` 内置基线起点，运行前检测缺失即自动补回并写回，同时打印告警（`ORIGIN_GUARD=0` 可关闭）。即使再被删，次日也会自愈。
3. **服务端加固**（commit `d9b1871b`）：两个起点接口补 `checkPin`；`checkPin` 改为 fail-closed（未设置 `ADMIN_PIN` 时拒绝所有写操作）；`verify-pin` 在 `ADMIN_PIN` 缺失时返回明确错误而非静默失败。

## 三之二、事件三：数据台 PIN 失效与全站无鉴权（P0，安全）

### 现象

用户输入原口令 `770108` 登录数据管理台失败。

### 排查结论：**口令没有被改，是环境变量丢了**

| 证据 | 结论 |
|---|---|
| `server.js` 中密码取自 `process.env.ADMIN_PIN`，代码内无任何硬编码口令 | 口令不在仓库，无法也不应被"查出" |
| `POST /api/verify-pin {"pin":"770108"}` → `{"ok":false}` | 当前 `ADMIN_PIN` 不是 770108 |
| `POST /api/verify-pin {"pin":""}` → `{"ok":true}` | **`ADMIN_PIN` 当前为空字符串** |
| `GET /api/kb`（需鉴权）不带 PIN → `200` | 全站写接口实际无保护，已确认 |

即：服务重启或重新部署后 `ADMIN_PIN` 未注入 → 值为空 → ① 任何口令都登不上（空串 ≠ 770108）；② `checkPin` 中空值恒真，所有写操作反而全部放行。

### 另：访问地址必须带分享参数

`https://a96a9f9fb53eefdca.app.workbuddy.host/data.html?sharecode=NE43RUUQXT` 返回 200；不带 `sharecode` 时托管层返回 403「链接不完整」。若曾出现打不开，先确认链接是否被聊天工具截断。

### 处置

- 服务端已改为 **fail-closed**：未设置口令时拒绝所有写操作并返回明确提示，**不会再出现"无口令也能改数据"**。
- 口令持久化改造（commit `79c953bc`）：取值优先级 ① 环境变量 `ADMIN_PIN` ② 服务端本地文件 `admin_pin.txt`；**每次请求实时读取，改口令免重启**；新增 `/api/set-pin`（首次设置 / 修改，≥4 位）与 `/api/pin-status`。
- 前端 `data.html`（commit `4d2f7c4c`）：锁屏页在服务端未设口令时自动展开「首次设置口令」表单，右上角新增「🔑 修改口令」入口，进入前会校验已存口令是否仍有效。
- `.gitignore` 已忽略 `admin_pin.txt`（commit `124af3b8`），避免口令误提交。
- 用户侧待办：**重启托管应用**（仓库更新不会自动部署），重启后打开数据台按提示首次设置口令即可，无需再依赖环境变量。详见 [数据台口令设置指南](./数据台口令设置指南.md)（已在数据台 `docs/收集箱/`）。

## 六、经验教训

1. **能写坏产物的代码必须有输出体检**。这次事故的本质不是「写错了数据」，而是「写错了语法且无人校验」——发布前的 V8 编译体检成本极低，却能完全拦住这一类故障。
2. **模板与产物要同等对待**。模板被写坏会污染之后每一天，危害远大于单日产物出错。
3. **外部系统覆盖式写入是隐形风险**。配置类文件被另一个自动化静默改写时，必须有人守卫或告警，否则只能靠人肉发现。
4. **「发布成功」不等于「页面可用」**。HTTP 200 与内容正确是两件事，校验必须落到渲染层。
5. **没有口令不等于没有权限**。鉴权缺失时系统不会报错，只会静默放行；「我没删过但数据没了」往往是接口裸奔，而不是灵异事件。
6. **环境变量类配置必须 fail-closed**。密钥为空时应拒绝一切写操作，而不是让空值通过相等判断——这次 `ADMIN_PIN` 丢失直接导致全站可读可写。
